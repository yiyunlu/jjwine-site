## 0. 结论摘要（先看这一节）

**问题**：基线 20 个漏洞（16 high / 2 moderate / 2 low），升级后剩 2 个 high（`vinext`、`image-size`），为什么清不掉？

**答案分两层**：

1. **`image-size` 清不掉，不是因为"上游还没修"，而是因为 `vinext@1.0.0-beta.2` 把 `image-size` 钉在 `2.0.2`**。advisory 的受影响区间是 `>=0.6.3 <=2.0.2`，而 registry 上 `2.0.3` / `2.0.4` 早已发布（`npm view image-size versions`，2026-09-25 实测）。`npm audit` 给的"唯一修法 = 升 `vinext@1.0.0-beta.12`"，只是因为 npm 默认不允许改传递依赖的版本，不代表没有别的修法。
2. **升 `vinext` 到 `1.0.0-beta.12` 确实能把 audit 清到 0，但代价是 `npm test` 从 44 pass 掉到 3 pass / 41 fail**（本次复跑实测；架构师在 49 项测试树上测得 3 pass / 46 fail）。根因已定位到具体一行：新版构建产物 `dist/server/index.js` 出现 `from"cloudflare:workers"`，Node 的默认 ESM loader 无法解析 `cloudflare:` 协议，测试套件在 **import 阶段**就崩了。这不是业务代码回归，而是**测试夹具（Node 直接加载 SSR 产物）与新版构建产物的契约断裂**。

**额外发现（本次复跑中新发现，架构师配方未包含）**：在**不动 `vinext`** 的前提下，仅加一条 `overrides` 把传递依赖 `image-size` 抬到 `^2.0.4`，`npm audit` 同样清到 **0**，且 `npm run lint` / `npm test`（44 pass / 0 fail）/ `npm run deploy:dry-run` **三条全 exit 0**，包体与 A1 升级后**完全一致**（1216.47 KiB）。

**推荐**：**采纳「路径 4：用 `overrides` 强制 `image-size@^2.0.4`」**，由车道 A 在既有 `package.json` 范围内追加实施。理由与风险见第 5 节；若项目安全策略明确禁止覆盖传递依赖，则退到路径 1（接受 2 个 high），**不建议**走路径 2。

## 3. 不可修部分的根因：`vinext` / `image-size`

### 3.1 关键事实一：`image-size` 的修复版本早已存在，只是被 `vinext` 钉死

```
$ npm view image-size versions --json | tail -5
  "2.0.1", "2.0.2", "2.0.3", "2.0.4"
$ npm ls image-size
jjwine-site@1.0.0
└─┬ vinext@1.0.0-beta.2
  └── image-size@2.0.2          ← 唯一的来源
```

advisory 受影响区间为 `>=0.6.3 <=2.0.2`（两条：`GHSA-5p2g-fcmc-qvqq` JXL/HEIF 解析死循环、`GHSA-w3rx-r6r6-pgpr` ICNS 解析死循环，均 `CVSS 7.5 / CWE-835`，仅 DoS，无 RCE / 无数据泄露）。`2.0.3` 与 `2.0.4` 已在受影响区间之外。

（来源：`npm view image-size versions --json`、`npm ls image-size`、`npm audit --json` 的 advisory 对象，2026-09-25，impl-b 实测）

### 3.2 关键事实二：升 `vinext@1.0.0-beta.12` 确实清 0，但测试全崩

### 3.3 与架构师数字的对照（必须说明的差异）

| 指标 | 架构师实测（卡面转述） | 本次复跑（impl-b） | 是否一致 |

**41 vs 46 的差异原因**：架构师测的是 **49 项**测试树（`3 + 46 = 49`），本次 worktree（`wt/b1-residual-report` @ `7caa1ee`）的 `package.json` 里 `scripts.test` 仍是 `node --test tests/rendered-html.test.mjs`，**只有 44 项**（`3 + 41 = 44`）。49 项那一版来自车道 T1（`<FACTORY_TASK_ID>`）尚未合并的 `tests/mobile-menu.test.mjs` + `tests/*.test.mjs` glob。**通过数同为 3、失败模式同为"除 3 项外全挂"，结论完全一致。**

（来源：`npm test` 输出，2026-09-25，impl-b 实测；A1/T1 卡面与评论）

### 3.4 根因定位（一行代码级别）

```
$ grep -roE "cloudflare:[a-z-]+" dist/server/index.js     # beta.12 构建产物
1 dist/server/index.js:from"cloudflare:workers"

$ grep -roE "cloudflare:[a-z-]+" dist/server/index.js     # 基线 beta.2 构建产物
(无匹配)
```

（来源：`grep`，2026-09-25，impl-b 在临时目录实测）

**因果链**：

1. `vinext` 自 `beta.6` 起，SSR 产物改为 `import ... from "cloudflare:workers"`；
2. `tests/rendered-html.test.mjs` 用 `node --test` + 动态 `import()` 直接加载 `dist/server/index.js` 来断言 SSR HTML；
3. Node 默认 ESM loader 只支持 `file:` / `data:` / `node:` 三种 scheme ⇒ **在 import 阶段抛错，44 项里除 3 项外全部失败**；
4. `wrangler deploy --dry-run` 仍 exit 0，因为 workerd 运行时**能**解析 `cloudflare:workers`。

**推论（标注为推论）**：因此这不是业务代码回归，而是**测试夹具与构建产物的契约断裂**——修 41 项失败的工作量落在"改造测试夹具"，不在"改业务代码"。这一点未经我验证到"改完就绿"，见第 6 节。

| `vinext` 版本 | `dependencies` 里有 `image-size`? | `peerDependencies["@vitejs/plugin-rsc"]` |

### 3.7 另一个被卡面配方忽略的前置障碍：peer 依赖冲突

```
$ npm install --save-dev vinext@1.0.0-beta.12      # 不动 @vitejs/plugin-rsc
npm error Conflicting peer dependency: @vitejs/plugin-rsc@0.5.35
npm error   peerOptional @vitejs/plugin-rsc@"^0.5.34" from vinext@1.0.0-beta.12
npm error Fix the upstream dependency conflict, or retry with --force or --legacy-peer-deps
```

用 `--legacy-peer-deps` 强行装上、保持 `@vitejs/plugin-rsc@0.5.26` 后，`npm test` 会在 **build 阶段直接死掉**：

```
Error: vinext: callable use cache requires @vitejs/plugin-rsc 0.5.34 or newer.
    at .../vinext/dist/plugins/use-cache-callable.js:101:52
```

（来源：`npm install` / `npm test`，2026-09-25，impl-b 在临时目录 `exp/beta12` 实测）

⇒ **"只升 `vinext`"在技术上不成立**：必须同时把 `@vitejs/plugin-rsc` 从 `0.5.26` 抬到 `>=0.5.34`。A1 卡面把"不升 `@vitejs/plugin-rsc`"列为红线是对的，但这也意味着路径 2 的实际改动面比卡面描述的更大（3 个包：`vinext`、`@vitejs/plugin-rsc`，以及连带重新解析的整棵 RSC 依赖）。

## 5. 推荐

### 5.1 明确推荐：采纳路径 4 —— 用 `overrides` 把 `image-size` 抬到 `^2.0.4`

**由车道 A（`package.json` 属主）追加实施，本卡不实施。**

推荐理由（每条都对应第 4 节的实测证据）：

1. **收益最大且已被实测**：`total 20 → 0`，`high 16 → 0`，`npm audit` exit 0（第 4.1 节）。这是四条路径里唯一"清到 0 且不牺牲任何现有能力"的选项。
2. **代价最小**：`package.json` 加 1 个 `overrides` 字段，`npm install` 只 `changed 1 package`；`lint` / `test`（44/44/0）/ `deploy:dry-run` 三条**全 exit 0**，包体与 A1 后**逐字节一致**（`1216.47 KiB`）。
3. **兼容性风险低且可验证**：`image-size` 在本仓库只被 `vinext/dist/server/metadata-route-build-data.js` 以 `import { imageSize }` 一处使用（构建期）；`2.0.2` 与 `2.0.4` 的导出集合实测完全一致。
4. **不触碰红线**：完全不动 `vinext`、不动 `@vitejs/plugin-rsc`、不动 `tests/`、不动 `app/`，与 A1 卡面"不升 `vinext`、不升 `@vitejs/plugin-rsc`"的红线一致。
5. **回滚成本最低**：删掉 `overrides` 段 + `npm install` 即回到 A1 后状态。

**实施要点（交给车道 A）**：

```jsonc
// package.json
"overrides": {
  "image-size": "^2.0.4"
}
```

验收应为：`npm audit --json` → `total: 0`（exit 0）；`npm run lint` / `npm test` / `npm run deploy:dry-run` 三条 exit 0；`npm test` 仍为 `44 pass / 0 fail`。

### 5.2 兜底（仅在 5.1 被否决时启用）：路径 1 —— 维持现状，接受 2 个 high

若项目安全策略**明确禁止**用 `overrides` 覆盖传递依赖（本卡未验证是否存在此类策略，见第 6 节），则退到路径 1，并按下述口径接受残余风险：

- 2 个 high 均为 **devDependency / 构建期**（`npm ls --omit=dev` 只有 `react`、`react-dom`；`image-size` 字符串不出现在 `dist/` 任何文件）；
- 两条 advisory 均为 `CWE-835` 死循环类 **DoS**，`CVSS 7.5`，无 RCE、无数据泄露；
- 触发条件要求攻击者能向构建期喂入恶意 JXL/HEIF/ICNS 图片——本仓库当前**没有**处理外部上传图片的构建流程。

### 5.3 明确不推荐：路径 2

**不建议**为了清这 2 个 dev 期 DoS 漏洞，去升 `vinext` 到 `beta.12`。理由：

- 代价与收益严重不成比例：**+222.42 KiB 包体（+18.3%）**、**44 → 3 pass（−41 项测试）**、外加改造测试夹具的工作量与回归风险；
- 被清掉的 2 个漏洞本来就不进 Worker 产物（第 1.4 节）；
- 会把改动面从"1 行配置"扩大到"`tests/` 夹具改造 + 3 个包的依赖重解析"，与 A1 卡面红线冲突；
- 唯一成立的理由是"必须用新版 `vinext` 的其他特性"，那是**功能驱动**的升级，应由独立卡片立项评估，而不是被 2 个 dev 期 advisory 推着走。
