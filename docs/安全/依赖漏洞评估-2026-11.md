### 3.1 `vinext` 链（4 个包：2 high + 2 moderate）

`npm ls`（只读）：

- `vinext@1.0.0-beta.2` → `@vercel/og@0.8.6` → `satori@0.16.0`
- `vinext@1.0.0-beta.2` → `image-size@2.0.2`

- `image-size` 与 `satori` 是漏洞源头，`@vercel/og`（经 `satori`）和 `vinext`（经 `@vercel/og`、`image-size`）是传导。`vinext` 因此是 high。
- 为何清不掉：`npm audit` 给的修法是 `npm audit fix --force`，会装 `vinext@1.4.2`，输出称其 "outside the stated dependency range"。`package.json` 把 `vinext` 精确钉在 `1.0.0-beta.2`，不带 `--force` 不会越过这个钉。2026-09 评估已发现把 `vinext` 升到 `1.0.0-beta.12` 会让 `npm test` 从 44 pass 掉到 3 pass / 41 fail（产物出现 `cloudflare:workers`，测试夹具无法加载），所以不在此处强行升级。

### 3.2 `minimatch` 链（13 个包，均 moderate）

`npm ls`（只读）：`eslint` 的 `@eslint/config-array`、`@eslint/eslintrc`，以及 `eslint-plugin-jsx-a11y`、`eslint-plugin-react` 使用 `minimatch@3.1.5`；`typescript-eslint` 经 `@typescript-eslint/typescript-estree` 使用 `minimatch@10.2.6`。两者都落在 `<11.0.1`。

传导到：`eslint`、`@eslint-community/eslint-utils`、`@typescript-eslint/{eslint-plugin,parser,type-utils,typescript-estree,utils}`、`typescript-eslint`、`eslint-plugin-jsx-a11y`、`eslint-plugin-react`。

为何清不掉：npm 对这条链只给 `npm audit fix --force`，输出写明 "Will install eslint-plugin-react@7.22.0, which is a breaking change"。`npm audit --json` 的 `fixAvailable` 指向的都是**降级**，不是升级：

`eslint` 9.39.4 到 4.0.0，`eslint-plugin-react` 7.37.5 到 7.22.0，`eslint-plugin-jsx-a11y` 6.10.2 到 6.4.1，`typescript-eslint` 8.59.3 到 8.14.0。

这些都标 `isSemVerMajor: true`。npm 没有给出可升级的修法；真正的修复要等上游发布不再依赖 `<11.0.1` `minimatch` 范围的新版本。

## 4. 影响范围（只陈述已查证的部分）

- npm 的分类：`npm audit --omit=dev` 修复前后都是 0，漏洞包都在 `devDependencies` 下。这是 npm 的依赖分类，**不等于运行时不可达**：`vinext` 的运行时代码会进入构建出的 worker。
- 当前构建的打包证据：head 构建的 50 个服务端 source map 列出 265 个 sources，其中 `node_modules` 下只有 `vinext`、`react`、`react-dom`、`react-server-dom-webpack`、`@vitejs/plugin-rsc`，没有来自 `image-size`、`satori`、`@vercel/og`、`minimatch` 的源码。客户端 chunk 没有 source map，但在 `dist/client` 中按字符串搜索，也找不到这四个名字。
- 局限：这只是对当前构建的检查，不保证未来的 `vinext` 版本也如此。复现：先构建，再列出每个 `dist/**/*.map` 的 `sources`。

### 4.1 行为核对（已做的与覆盖范围）

本变更只改锁文件，不改 `package.json`。已核对：

- 在全新 `npm ci` 后，本提交上 lint 通过（与基线相同的 6 个 warning），`npm test` 104/104 通过，`wrangler deploy --dry-run` 通过；tsc 只报与基线相同的 4 个已有错误，没有新增。
- `/en`、`/zh-cn`、`/es` 的服务端渲染 HTML 与响应头和基线 `dae973c` 一致。比较时忽略构建产物的哈希文件名和每次构建的 `deploymentVersion`，并把每个 RSC 客户端模块 id 换成构建资源清单里的导出名和 chunk 依赖。

- 客户端 JS chunk **不是**字节级一致：vite 8.3.1 到 8.3.5、rolldown 1.2.11 到 1.2.16 会重新打包。
- 在 390px 视口对构建后的 worker 做了浏览器检查：React 完成 hydration，移动菜单可用 Enter 打开、Escape 关闭。

除此之外没有声明更多的等价性。

## 6. 复现方法

registry 为 `https://registry.npmjs.org/`。

1. 在基线 `dae973c` 上执行 `npm ci`、`npm audit --json`、`npm audit --omit=dev --json`，得到修复前数字。
2. 在同一目录执行 `npm audit fix`（不带 `--force`），得到的 `package-lock.json` 即本提交的锁文件。
3. 在本提交上执行 `npm ci`、`npm audit --json`、`npm audit --omit=dev --json`，得到修复后数字。
4. 执行 `npm ls image-size satori @vercel/og minimatch` 查看依赖链。
